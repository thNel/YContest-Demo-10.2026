# Пояснительная записка: «Восстановление мозаики»

## Суть задачи

Есть `N` различных частей мозаики, пронумерованных от `1` до `N`. Каждая часть должна находиться ровно в одной позиции от `1` до `N`, но соответствие «часть → позиция» неизвестно.

Разрешены запросы `CHECK`: можно выбрать произвольное множество частей, а в ответ получить множество позиций, в которых находятся эти части.

При этом соответствие внутри запроса теряется: если отправлены части `2, 5, 7`, в ответ приходят только позиции этих трёх частей в отсортированном виде. Нельзя напрямую понять, какая позиция относится к какой конкретной части.

Ограничение — не более 10 запросов, при этом `N ≤ 500`.

## Основная идея

Каждой части назначается уникальный двоичный код.

Для части с номером `p` используется число:

```text
p - 1
```

Так как:

```text
N ≤ 500
2^9 = 512
```

достаточно 9 бит.

Каждый запрос отвечает за один бит этого кода.

## Построение запросов

Для номера бита `b` выбираются все части, у которых этот бит в числе `p - 1` равен единице.

Например, для четырёх частей:

```text
часть 1 -> 0 -> 00
часть 2 -> 1 -> 01
часть 3 -> 2 -> 10
часть 4 -> 3 -> 11
```

Для младшего бита единица стоит у частей `2` и `4`.

Для старшего бита единица стоит у частей `3` и `4`.

Именно эти множества и отправляются в соответствующих запросах.

## Почему ответы позволяют восстановить порядок

Предположим, реальный порядок частей:

```text
позиция: 1 2 3 4
часть:   4 2 1 3
```

Коды частей:

```text
1 -> 00
2 -> 01
3 -> 10
4 -> 11
```

### Запрос по младшему биту

Выбираются части `2` и `4`.

Они находятся в позициях `2` и `1`, поэтому ответ содержит:

```text
1 2
```

После этого известно:

```text
позиция 1 -> младший бит 1
позиция 2 -> младший бит 1
позиция 3 -> младший бит 0
позиция 4 -> младший бит 0
```

### Запрос по старшему биту

Выбираются части `3` и `4`.

Они находятся в позициях `4` и `1`.

Ответ:

```text
1 4
```

Добавляем старший бит:

```text
позиция 1 -> 11
позиция 2 -> 01
позиция 3 -> 00
позиция 4 -> 10
```

Теперь код каждой позиции совпадает с кодом лежащей там части.

Следовательно:

```text
11 -> часть 4
01 -> часть 2
00 -> часть 1
10 -> часть 3
```

Порядок полностью восстановлен.

## Что хранится для каждой позиции

Используется массив:

```text
code[position]
```

Изначально все значения равны нулю.

Если позиция появилась в ответе на запрос по биту `b`, этот бит устанавливается:

```text
code[position] |= 1 << b
```

После выполнения всех запросов:

```text
code[position] = номер_части - 1
```

поэтому:

```text
номер_части = code[position] + 1
```

## Почему сортировка ответа не мешает

Интерактор возвращает позиции по возрастанию, поэтому соответствие «выбранная часть → позиция» внутри одного запроса действительно теряется.

Но алгоритму это соответствие и не нужно.

Каждый запрос задаёт только один бинарный вопрос:

> На каких позициях находятся части, у которых данный бит кода равен 1?

Если позиция присутствует в ответе, для неё устанавливается соответствующий бит.

Полный номер части складывается из результатов всех запросов.

## Количество запросов

Необходимо:

```text
ceil(log2 N)
```

запросов.

При `N = 500`:

```text
ceil(log2 500) = 9
```

Это меньше разрешённых 10.

Для `N = 1` запросы не нужны: единственная часть находится в единственной позиции.

## Формат интерактивного обмена

После `CHECK` выводятся номера выбранных частей.

Отдельное число, обозначающее количество частей, не выводится: количество определяется самим числом перечисленных элементов.

После каждого запроса нужно немедленно отправить строку интерактору и только затем ждать ответ.

В JavaScript это удобно делать через `process.stdout.write(...)` с ожиданием callback записи. Это исключает зависание из-за того, что программа уже ждёт ответ, а запрос ещё не был передан интерактору.

## Сложность

Количество запросов:

```text
O(log N)
```

В каждом запросе просматриваются все `N` частей:

```text
O(N log N)
```

Память:

```text
O(N)
```

## Почему выбран именно этот подход

Один запрос возвращает для каждой позиции ровно один признак: принадлежит ли лежащая там часть выбранному множеству.

Это естественно интерпретируется как один бит информации.

Если каждому объекту назначить уникальную битовую маску, последовательность ответов для каждой позиции становится этой маской.

Таким образом, интерактивная задача сводится к двоичному кодированию идентификаторов, а ограничение в 10 запросов напрямую связано с тем, что девяти бит уже достаточно для кодирования всех `N ≤ 500` частей.
